1. Whole-System Overview

Short defense explanation

“Our Academic Evaluation System uses a client-server architecture. The React frontend is responsible for the user interface, role-based portals, forms, reports, and interaction. It communicates with a Laravel REST API through Axios. The backend authenticates the user, validates requests, applies academic and permission rules, reads or updates the MySQL database, and returns JSON. React stores the returned data in component state and automatically updates the page.”

Frontend responsibilities

  • Display pages appropriate to the user’s role and permissions.
  • Collect input and provide immediate form feedback.
  • Send authenticated API requests and display responses.
  • Handle responsive layout, accessibility, reports, and exports.

Backend responsibilities

  • Authenticate JWTs and enforce authoritative access rules.
  • Validate requests and academic operations.
  • Persist curricula, evaluations, users, and related records.
  • Provide auditing, imports, analytics, and database backups.
Important defense point: The frontend may hide a page or button, but that is only a usability control. Real security must be enforced by backend middleware and controller permission checks.

2. Example: Student Evaluation Flow

  1. A permitted staff member opens the shared student evaluation workspace.
  2. React requests the student directory and the selected student’s academic record.
  3. Axios attaches the saved JWT as a Bearer token.
  4. Laravel verifies the JWT and evaluation access before running the controller.
  5. The backend loads curriculum, grades, prerequisites, electives, standing, and transfer credits.
  6. The evaluator edits grades or plans in React state and confirms the action.
  7. Laravel validates and saves the permitted operation, then returns JSON.
  8. The frontend reloads the record and shows the updated evaluation or report.

State and storage

  • React state: live page, form, filter, modal, and API data.
  • Context: authenticated user and guide state.
  • localStorage: JWT, tab/sidebar preferences, guide status, and some evaluation plans.
  • sessionStorage: recoverable non-password form drafts.

Accessibility and responsiveness

  • Skip link and semantic main content.
  • Visible keyboard focus and reduced-motion support.
  • Focus trapping and restoration for shared dialogs.
  • Keyboard-accessible tabs and searchable selects.
  • Responsive layouts and sidebar behavior.
Verified frontend limitations:
  • There are currently no frontend test files, and CRACO removes ESLint from webpack compilation.
  • The JWT is stored in localStorage, making strong XSS prevention essential.
  • /student requires login but does not explicitly require the Student role.
  • Unknown URLs have no catch-all 404 route.
  • Evaluation row saves use separate concurrent requests, so partial persistence is possible.
  • StudentEvaluationView.js is over 8,000 lines and combines many responsibilities.
  • html2canvas-based PDFs are rasterized and are less searchable and accessible.

5. Backend Architecture

Laravel 12 PHP 8.2+ JWT Auth Eloquent ORM MySQL

Backend defense script

“The backend is a Laravel REST API. Requests enter through routes/api.php. Middleware checks the JWT, unsafe input, and evaluation access. The matching domain controller validates the request and coordinates models or services. Services contain complex rules such as authentication security, academic standing, prerequisites, promotion, imports, transfer credits, and backups. Eloquent models represent database tables and relationships. Laravel then returns JSON to the frontend, while audit observers record important model changes.”

8. Security and Reliability

  • auth:api uses JWT and the TblUser provider.
  • SecurityHeaders adds browser security policies to responses.
  • RejectUnsafeInput checks API input and normalizes contact numbers.
  • EvaluationAccessMiddleware checks evaluation privileges and restricts deletion.
  • Laravel request validation rejects invalid payloads with HTTP 422.
  • Transactions protect many multi-table imports, evaluations, promotions, and credit operations.
  • AuditModelObserver records important model changes.

9. Database, Operations, and Verified Limitations

Database lifecycle

  • 81 migrations record incremental schema changes.
  • 11 seeders provide permissions, users, subjects, electives, and demonstration records.
  • Most models map legacy tbl_* names and custom primary keys.

Operational tools

  • scripts/imports/: one-off curriculum imports.
  • scripts/maintenance/: repair and cleanup utilities.
  • storage/app/backups/: generated database backups.
  • Scheduled commands handle INC expiry and backup checks.
Verified backend limitations:
  • POST /api/jwt/register is public and accepts a caller-selected existing role_id. This can allow privileged self-registration unless restricted before deployment.
  • Comments saying “admin only” are not enforcement. Many permissions are checked inside controllers rather than attached directly to route groups.
  • Fresh migrations do not create several foundational legacy tables, including users, students, subjects, programs, and campuses.
  • The setup instructions reference capstone_db.sql, but that file is absent. An empty database therefore cannot currently be rebuilt reliably from the repository alone.
  • Backend automated coverage contains only two unit-test suites and does not exercise controllers, MySQL schema, imports, or backups.

10. Common Defense Questions

QuestionBrief answer
Why separate frontend and backend?It separates presentation from business rules and data access, allowing each side to be developed, tested, and secured independently.
Why use JWT?It lets the stateless API identify authenticated users through a signed Bearer token on each protected request.
Why use services?Services isolate complex reusable rules and prevent large controllers from duplicating domain logic.
Why use migrations?They provide an ordered, version-controlled history of database changes. In this project they currently supplement, rather than fully replace, the legacy base schema.
How are roles controlled?The backend provides role and permission data; the frontend filters modules, while the backend must authorize sensitive API operations.
How is data consistency protected?Laravel validation, foreign keys, transactions, controller checks, and audit logging protect many operations. Known non-atomic frontend save flows remain improvement targets.

This guide describes the verified repository structure as of September 2026. Identified limitations are included so the architecture can be defended accurately rather than overstated.
